## 1. 装依赖：7 个包，分四组

```bash
npm i -D eslint @nuxt/eslint @stylistic/eslint-plugin   # 第一组：检查器本体
npm i -D typescript vue-tsc @types/node                 # 第二组：类型检查
npm i -D husky lint-staged                              # 第三组：钩子
```

| 包 | 作用 | 不装会怎样 |
|---|---|---|
| `eslint` | 检查器**本体**（引擎 + 核心规则） | 没有 `npx eslint` 命令 |
| `@nuxt/eslint` | Nuxt 官方适配层。① `nuxt prepare` 时生成 `.nuxt/eslint.config.mjs`，把 Nuxt 的**自动导入 API**（`ref`、`useAsyncData`、`definePageMeta`…）注册成 globals；② 提供 Vue/TS 推荐规则集 | 每行 `ref()` 都会报 `no-undef`，几百条假错 |
| `@stylistic/eslint-plugin` | 格式规则（缩进、引号、逗号、箭头函数括号），**替代 Prettier** | 格式风格不统一；或再装 Prettier，两个格式化器互相覆盖 |
| `typescript` + `vue-tsc` | 类型检查。`vue-tsc` 是 `tsc` 的 Vue 方言版，能进 `.vue` 模板里查类型 | 上一轮的 11 个类型错一个都发现不了 |
| `@types/node` | Node 内置 API 的类型（`Buffer`、`process`）。Nitro 服务端代码要用 | `Buffer` 报"找不到名称" |
| `husky` | 把 git hook 变成"随仓库分发"的机制 | 钩子只能手写在 `.git/hooks`，别人 clone 后没有 |
| `lint-staged` | 从暂存区挑出改动文件，只对它们跑命令 | 每次 commit 全量 lint，40 秒起步，人就开始 `--no-verify` |

**为什么用 `-D`（devDependencies）**：这些工具不进运行时代码，不需要打包，也不该让服务器多装几十 MB。

## 2. 注册模块：`nuxt.config.ts` 第 4 行

```ts
modules: ['@pinia/nuxt', '@nuxt/eslint'],
```

作用：让 `@nuxt/eslint` 在 `nuxt prepare` 时生成配置文件。
`npm install` 结束后 `postinstall: nuxt prepare` 触发它生成 `.nuxt/eslint.config.mjs`——该文件在 `.gitignore` 里，不进仓库，每次装依赖重造。

## 3. `eslint.config.mjs` 逐行

```js
// @ts-check                                        // ①
import withNuxt from './.nuxt/eslint.config.mjs'    // ②

export default withNuxt({                           // ③
  rules: {
    'no-unused-vars': 'off',                        // ④
    '@typescript-eslint/no-unused-vars': ['error', {// ⑤
      argsIgnorePattern: '^_',
      varsIgnorePattern: '^_',
      caughtErrors: 'none',
    }],
    'no-console': ['warn', { allow: ['warn', 'error'] }],  // ⑥
    'vue/multi-word-component-names': 'off',        // ⑦
  },
})
```

### ① `// @ts-check`
让编辑器对这个 JS 文件跑类型检查。写错规则名（`no-console` 打成 `no-consoles`）会当场标红，而不是运行时静默失效。

### ② `import withNuxt from './.nuxt/eslint.config.mjs'`
从 Nuxt 生成的配置里导入"包装器"。该文件由 `@nuxt/eslint` 产出，已拼好：Nuxt globals + Vue 规则 + TS 解析器 + 忽略目录（`.nuxt`、`dist`、`node_modules`）。

### ③ `withNuxt({...})`
把自己的配置**追加**在 Nuxt 那套之后（flat config 本质是数组，后者覆盖前者）。
不写这一层直接 `export default [{...}]`，Nuxt 的 globals 全丢 → `ref` 报未定义。

### ④ `'no-unused-vars': 'off'`
关掉 ESLint **核心版**规则。核心版不认识 TS 语法，遇到 `import type { Foo }`、泛型、interface 会瞎报，改由 TS 版接手。

### ⑤ `'@typescript-eslint/no-unused-vars': ['error', {...}]`
- **`'error'` 而非 `'warn'` 是本项目最关键的一条设定**：只有 error 会让 `eslint` 以非 0 退出码失败，钩子才拦得住提交。warn 只是屏幕上一行黄字。
- `argsIgnorePattern: '^_'`：参数名以 `_` 开头视为"故意不用"（`function f(_e, id)`），不报。
- `varsIgnorePattern: '^_'`：变量同理。
- `caughtErrors: 'none'`：`catch (e) {}` 里没用 `e` 不报——项目里大量 `catch {}` 只弹 toast，全报太吵。

> ⚠️ 注意边界：这条查的是"**定义了没用**"。而"**用了没定义**"（漏导入，本项目栽过 3 次）归 `no-undef` 与 tsc 的 `2304` 管，两道都开着才不留死角。

### ⑥ `'no-console': ['warn', { allow: ['warn', 'error'] }]`
`console.log` 提示但**不阻塞提交**（调试期谁都会留）；`console.warn/error` 放行（线上错误上报常用）。

### ⑦ `'vue/multi-word-component-names': 'off'`
Vue 官方要求组件名至少两个单词（避免和 `<div>`、`<table>` 撞名）。但 Nuxt 文件路由约定名就是 `index.vue`、`cart.vue`、`login.vue`——**改不了名**，这条必须关，否则全站爆红。

## 4. lint-staged 范围：在 `package.json` 底部

```json
"lint-staged": {
  "*.{js,mjs,ts,vue}": "eslint --fix"
}
```

- **key 是 glob**：只挑 `.js/.mjs/.ts/.vue` 四种扩展名。没放 `.scss`/`.json`，因为 ESLint 查不了样式；等用上 stylelint 再加一行。
- **value 是命令**：对这批文件跑 `eslint --fix`。

### 工作机制（三步，面试常问）

1. `git commit` 触发 → 执行 `git diff --cached --name-only`，拿到**暂存区**文件列表（不是整个工作区）
2. 用 glob 过滤，只留改动过的代码文件，拼到命令后面：
   `eslint --fix app/pages/cart.vue app/stores/cart.ts`
3. **若 `--fix` 改动了文件，自动帮你重新 `git add`**——否则修好的格式留在工作区，提交进去的还是旧内容。之后仍有 error 没修掉，非 0 退出，提交被拦。

**为什么用 `--fix` 而不是纯检查**：能自动修的（缩进、引号）直接修好，人无感；修不了的（未使用变量）才报错让你判断。上一轮 261 条就是被它静默修掉的。

## 5. `.husky` 两条命令

```sh
# .husky/pre-commit
npx lint-staged

# .husky/pre-push
npm run typecheck
```

husky v9 只需这两行，**不需要** `#!/usr/bin/env sh`，也不需要 `. "$(dirname "$0")/_/husky.sh"`（v8 及以前才要）。

### 让它们生效的三处机制

**1. `git config core.hooksPath` = `.husky/_`**
git 只认 `.git/hooks/` 下的固定文件名（`pre-commit`、`pre-push`…）。husky 把 git 的视线改到 `.husky/_`，那里放了一批**转发脚本**，收到调用后回头执行 `.husky/pre-commit`（你写的那行）。这就是用户文件里不需要 shebang 的原因。

**2. `.husky/_/` 是运行时，不进仓库**
husky 在里面放了 `.gitignore`，内容是一个 `*` ——整个目录自我忽略。所以提交时只带上 `pre-commit`、`pre-push` 两个文件（各 1 行）。

**3. `"prepare": "husky"` 写在 package.json scripts 里**
`npm install` 结束后自动执行，重建 `.husky/_` 运行时。**这就是"别人 clone 下来装个依赖就自动有钩子"的原因**，无需记得手动 `husky init`。

### 为什么拆成两档（设计决策，不是随便放）

| 钩子 | 跑什么 | 耗时 | 放错会怎样 |
|---|---|---|---|
| pre-commit | 只查暂存文件 | ~1 秒 | 每次提交等 40 秒 → 人开始 `--no-verify` → 钩子形同废除 |
| pre-push | 全量 typecheck | ~40 秒 | 放 pre-commit 就是上一条 |

## 6. `.github/workflows/ci.yml` 逐行

```yaml
name: CI                                    # ① 工作流名，显示在 Actions 页与 PR 检查里

on:                                         # ② 触发条件
  push:
    branches: [main, dev]
  pull_request:
    branches: [main, dev]

concurrency:                                # ③ 取消过期任务
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  quality:
    name: Lint · Typecheck · Build
    runs-on: ubuntu-latest                  # ④ 跑在 GitHub 提供的 Linux 虚拟机
    steps:
      - uses: actions/checkout@v4           # ⑤ 把仓库代码拉到 CI 机器
      - uses: actions/setup-node@v4
        with:
          node-version: 22                  # ⑥ 与本地 nvm 版本对齐
          cache: npm                        # ⑦ 缓存 ~/.npm，第二次起快很多
      - run: npm ci                         # ⑧ 不是 install
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run build                  # ⑨ 构建也要跑
        env:
          NODE_OPTIONS: --max-old-space-size=4096   # ⑩ 放大堆内存
```

**② 只监听 `main`/`dev`**：避免每个临时分支一推就跑，浪费每月免费额度。

**③ `concurrency` + `cancel-in-progress`**：同一分支连续推两次，取消上一次未跑完的——省时间也省额度。

**⑥ `node-version: 22`**：必须与本地一致，否则出现"CI 过、本地红"（或反之）。

**⑦ `cache: npm`**：内置缓存，key 自动绑定 `package-lock.json` 的哈希，锁文件变了才重新下载。

**⑧ `npm ci` 而不是 `npm install`**：严格按锁文件安装，**不会顺手把 `^` 范围内的小版本升级**。`install` 在 CI 上可能装出与本地不同的依赖树，产生"CI 红了本地绿的"玄学。CI 场景永远用 `ci`。

**⑨ 跑 build 的理由**：lint 与 typecheck 都是静态分析，看不到"SSR 构建时 Nitro 打包失败""服务端误用浏览器 API"这类错。构建能过 = 真的能部署。

**⑩ `--max-old-space-size=4096`**：Nuxt SSR 构建峰值内存较高，GitHub 免费机器默认堆偏小，容易 OOM 失败。

### 本地已有钩子，为什么还要 CI

钩子能被 `git commit --no-verify` 绕过，CI 不能。两者是**互补而非重复**——本地是"快速反馈"，CI 是"不可绕过的最终闸门"。

## 7. 附加：`.editorconfig` 与 4 个 scripts

```ini
root = true              # 到此为止不再向上层目录找配置

[*]                      # 所有文件
charset = utf-8
indent_style = space     # 缩进用空格
indent_size = 2          # 2 个（前端主流，ESLint stylistic 也是 2）
end_of_line = lf         # 换行符统一 LF —— Windows 上尤其重要
insert_final_newline = true       # 文件末尾留空行（diff 更干净）
trim_trailing_whitespace = true

[*.md]
trim_trailing_whitespace = false  # Markdown 里行尾两个空格 = 换行，不能删
```

它管的是**编辑器层面**（VS Code、Cursor、IDEA 都读），保存时就统一；ESLint 管的是**提交层面**。两者不冲突，是"早一步"与"晚一步"。

`package.json` 新增的 4 个脚本：

```json
"lint": "eslint .",            // 全量检查，人肉主动跑
"lint:fix": "eslint . --fix",  // 全量检查 + 自动修
"typecheck": "nuxt typecheck", // 内部调 vue-tsc，读 .nuxt 的四套 tsconfig
"prepare": "husky"             // npm install 后自动装钩子运行时
```

## 8. 新项目照抄这套的完整顺序

```bash
npm i -D eslint @nuxt/eslint @stylistic/eslint-plugin typescript vue-tsc @types/node husky lint-staged
# nuxt.config.ts → modules 数组加 '@nuxt/eslint'
# 新建 eslint.config.mjs（15 行）
# package.json → 加 4 个 scripts + lint-staged 字段
npx husky init                     # 生成 .husky/ 与 prepare 脚本
printf 'npx lint-staged\n' > .husky/pre-commit
printf 'npm run typecheck\n' > .husky/pre-push
# 新建 .github/workflows/ci.yml（35 行）
npm run lint -- --fix              # 存量收敛（格式）
npm run typecheck                  # 类型收敛
```

五件手动的事加起来不到一小时。**真正花时间的是收敛阶段**（本项目 265 条 → 0）——而那部分恰恰是工具干活、你做判断。

## 9. 人工 / 自动的分界线（结论）

| 类别 | 内容 |
|---|---|
| **人工 · 只做一次** | 选型装依赖、写 lint 规则档位、写 lint-staged 范围、写 husky 两条命令、写 CI、存量收敛时判断每条怎么修、故意犯错验证钩子真拦、写报错手册 |
| **自动 · 每次都跑** | 写代码时编辑器实时标红、commit 查暂存文件（~1s）、push 全量 typecheck（~40s）、推远端 CI 跑 lint+typecheck+build |
| **永远不会自动（必须人判断）** | 规则该多严（error 还是 warn）；报错怎么修（`'foo' is defined but never used` 可能是"删掉"也可能是"你忘了用它"）；CI 红了谁去看 |

**一句话**：工程化投的是"判断"，换来的是"执行"的零成本。

本项目最有说服力的注脚：ESLint 首轮 265 条问题里，`--fix` 自动修掉 261 条，剩下 **4 条全是真问题**，其中 1 条是**功能 bug**——搜索页的 `onConfirm`（回车搜索 + 记历史）从未绑定到 `<Search @search>`，功能一直处于死状态。静态检查的价值不是规范格式，而是**发现你以为已经做好的事其实没做**。
